原理

以人类竞赛的组别为难度标尺，从官方来源构建五档题库；按官方时限判题，与官方解比较运行效率与复杂度，并报告输出 token、输出速度与费用。

建库

下载官方题面、测试数据与题解，用判题程序运行全部官方解；没有官方解能通过的题剔除。

生成

每个采样调用一次模型，取回答中最后一个对应语言的代码块。

判题

在评测机本机按官方时限运行全部测试点，按来源的官方规则计分。

效率与质量

与官方解比较 CPU 时间、内存与复杂度增长幂次；Python 档另测静态代码质量。

统计

按题重抽样的 bootstrap 区间、配对差值与逐题符号检验。

阶梯基准

  • 难度用人类标尺划分。USACO [1] 的铜、银、金、铂金四个组别由真实选手的晋级线划定，EGOI [2] 是国际奥赛；档位反映的是人类选手的水平，而不是某个模型觉得难不难。
  • 只用官方数据。AtCoder 自 2024 年 12 月起不再公开测试数据，LeetCode 的测试不公开且用户协议禁止批量抓取，这两个来源都给不出可信的标准答案，因此没有采用。
  • 高档用连续分。USACO 按测试点给部分分，EGOI 按子任务给分，FrontierCS [3, 4] 由 checker 给出连续分，高档不会像通过率那样很快饱和。
  • 按官方时限判题。每个测试点按实际 CPU 时间判定是否在官方时限内完成，与人类选手的判题条件一致。
  • 先验证判题本身。建库时先用判题程序运行官方题解；没有任何一份官方解能全部通过的题直接剔除，这同时检验了测试数据、比对规则与判题程序。能通过的官方解中最快的一份作为该题的性能对照。

USACO 取 2024–25 赛季的 12 月、1 月、2 月与美国公开赛共 4 场，以及 2025–26 赛季的 3 场线上赛（3 月的公开赛为线下监考赛，官网没有公布题目与测试数据）。EGOI 2026 共 8 题，其中 Census 与 Seating Plan 为交互题，不在题库中。IOI 2026 的题目为通信题或只提供 PDF 题面，未纳入。FrontierCS 的题库有 180 道开放式难题，没有类别标签，按题号均匀抽取 30 题。测试数据只存放在评测服务器上，不公开；各题的英文原题面见 题目。

判题与计分

判题在评测服务器本机进行，所有模型使用同一套题目、判题程序与计分规则。

  • 运行环境。答案以无特权用户运行，由一个小的启动器设置地址空间（内存上限加 64 MB）、栈、CPU 时间与输出大小（256 MB）上限，并把进程绑定在一个独占的核上；CPU 时间与峰值内存取自子进程自身的资源统计。CPU 时间超过官方时限的测试点判为超时。
  • 语言。Python 档使用 CPython 3.11、只允许标准库，官方时限沿用 USACO 给 Python 的时限；C++ 档以 g++ -O2 -std=gnu++17 编译。
  • 比对。USACO 忽略空白逐个 token 比对，与其官方规则一致；EGOI 使用官方 checker；FrontierCS 使用官方的 testlib checker 或交互器，并照搬其判分规则，只解析 checker 输出的得分比例。

计分

每个测试点 t 得分 st ∈ [0, 1]：编译失败、运行出错、超时或超内存记 0。每题得分 S（0–100）按来源的官方规则计算：

  • USACO：S = 100 · (1/T) · Σt st，即测试点等分。
  • EGOI：S = 100 · Σg wg · mint∈g st / Σg wg，即子任务 g 取其中测试点的最低分，再乘以子任务分值。
  • FrontierCS：所有测试点得分比例的平均乘以 100；达到参考解为 60 分，超过参考解越多得分越高。

所有测试点都满分才算“解出”。L1、L2、L5 每题采样 1 次，L3、L4 每题采样 3 次，以减小高档题少带来的随机误差。pass@1 [5] 是解出的采样占全部采样的比例，平均得分是全部采样的 S 的平均，pass@3 是 3 次采样中至少一次解出的题所占比例。L5 为连续分，只报告平均得分。

运行效率、复杂度与代码质量

与 EffiBench [6]、ENAMEL [7] 一样，只在答案正确的前提下比较效率；基准是官方解，而不是模型之间互相比较 [8]。

  • 运行效率。只对解出的答案、且官方解在某个测试点上至少需要 0.05 秒 CPU 的题比较运行时间：取官方解最慢的 3 个测试点，答案与官方解交替各运行 3 次取中位数，倍数为答案的 CPU 时间除以官方解的 CPU 时间，各档取几何平均。峰值内存倍数同理。
  • 复杂度。官方测试点未按规模排列，USACO 中耗时可测的测试点几乎都是最大规模，直接按输入大小拟合不可行 [9]。因此以官方解自身的耗时作为规模的度量：在官方解至少需要 2 ms CPU 的测试点上（最多 20 个，均匀覆盖其耗时范围），答案与官方解交替各运行 5 次取中位数，拟合 log y答案 = a + k · log y官方。若官方解为 Θ(f(n))、答案为 Θ(f(n)k)，k 即为这个指数。只在 R² ≥ 0.8 时下结论：k ≤ 0.75 且在官方解最重的 3 个测试点上答案至少快 2 倍为更优，0.75 < k < 1.33 为同阶，k ≥ 1.33 且至少慢 2 倍为更差，其余为不确定；可用测试点少于 4 个或官方耗时跨度不足 4 倍为不可测。
  • 静态代码质量。对 L1、L2 中解出的 Python 答案，按 Huang 等人 [10] 的工具与版本，报告 Pylint 3.3.5 的问题数与 0–10 分，以及 Radon 6.0.1 的圈复杂度、可维护性指数（MI）与代码行数（SLOC）。
  • 用量、速度与费用。每个采样对应一次调用。输出 token 为接口计费的输出用量，含思考过程；延迟为调用从发出到接收完毕的时间；首个 token 时间为从发出到收到第一个 token 的时间；输出速度为输出 token 除以首个 token 之后的时长（tokens/s）。费用按各家的官方美元标价计算：（输入 − 缓存命中）× 输入单价 + 缓存命中 × 命中单价 + 输出 × 输出单价，分时计价按每次调用的开始时间。

统计方法

模型之间的比较以题目为单位。各档指标的 95% 区间来自 B = 2000 次按题重抽样（随机种子 0）[11]：每次在每档内部有放回地抽取同样数量的题，重新计算各档与 L1–L4 合计的 pass@1 与平均得分，取 2.5% 与 97.5% 分位数；两个模型使用同一组题（配对 bootstrap），从而消除题目难度带来的共同波动。逐题比较取每题所有采样的平均得分，相差不到 0.05 分记为持平，并对胜负题数做精确符号检验。

调用设置

三个模型都通过各自厂商的官方接口流式调用。MiniMax 的 temperature 为 0.2、top_p 为 0.95（沿用 LiveCodeBench 的设置）；DeepSeek 在思考模式下不支持 temperature 参数 [12]；Kimi 不传 temperature 与 top_p，使用接口默认值。

提示词

USACO 与 EGOI 题沿用 LiveCodeBench [14] 的写法，并给出时限与内存限制；FrontierCS 使用其官方生成脚本的原始提示词，便于与其公开排行榜对照。答案取回答中最后一个对应语言的代码块，没有对应语言时取最后一个代码块。

  • Python 档系统提示词：You are an expert Python programmer. You will be given a question (problem specification) and will generate a correct Python program that matches the specification and passes all tests.
  • C++ 档系统提示词：You are an expert competitive programmer. You will be given a question (problem specification) and will generate a correct and efficient C++17 program that matches the specification and passes all tests.
  • 用户消息：### Question: 之后为题面，随后一行写明时限、内存限制与语言（如 Time limit: 2 seconds per test. Memory limit: 256 MB. Compiled with g++ -O2 -std=gnu++17.），再给出格式说明：Read the inputs from stdin solve the problem and write the answer to stdout (do not directly test on the sample inputs). Enclose your code within delimiters as follows.
  • FrontierCS：You are a competitive programmer. You will be given a problem statement, please implement a solution in C++. The execution time and memory limit are also stated in the statement so be aware of the complexity of the program. Please wrap the code in ```cpp and ``` so that it is properly formatted. Your response should ONLY contain the C++ code, with no additional explanation or text.

被测模型

三个模型都在 2026 年 9–10 月发布，都默认开启思考。以下内容来自厂商的技术博客、技术报告、模型卡与接口文档，分数为厂商自报。

Kimi K3.1 Pro

月之暗面于 2026 年 10 月 23 日发布，官方称它是 Kimi K3 的后训练版本，使用了大得多的后训练算力，并在数百个下游领域上联合做强化学习 [15]；K3 为 MoE 架构，总参数 2.8T、每 token 激活 104B，上下文 1M [16]。代码方面，官方称 K3.1 Pro 覆盖从真实代码库中的快速修复到完整项目构建的全部编程工作，并以大规模强化学习增强长程编程；自报 Terminal-Bench 4.0 65.7%（Claude Code 框架），内部的 Kimi Code Bench 3.0 长程子集 61.2%（K3 为 55.95%）。官方成绩使用 max 思考强度、temperature 1.0、top-p 0.95；另有 Highspeed 版本（kimi-k3.1-pro-highspeed），称速度为 K3.1 Pro 的 2–3 倍。思考不能关闭，强度可选 low、high、max，不指定时默认 max [13]。官方没有报告竞赛编程成绩。

DeepSeek Flash V4.1-1017

DeepSeek 于 2026 年 9 月 10 日发布 V4.1-Flash，10 月 17 日更新为 1017 版，接口名与价格不变，以 MIT 许可开放权重 [17]。模型为多模态 MoE，主干 552B 参数、每 token 激活 8B（prefill）/ 16B（decode），另有 196B 的 Engram 条件记忆，上下文 1M。技术报告 [18] 的主要创新在注意力与 KV cache 的压缩，面向长上下文与“输入很重”的智能体场景的服务成本；报告明确说后训练“没有算法上的创新”，沿用监督微调、强化学习与在线蒸馏的标准流程，改动都在数据上，并在训练中按思考深度施加长度惩罚，使深度可调。报告称其 Codeforces 评分（内部评测）为 3471，高于 V4-Flash 的 3289 与 V4-Pro 的 3348。1017 版称以自反馈强化学习改进端到端的项目开发，并缩短了任务耗时与输出长度；厂商自报（智能体框架）Terminal-Bench 4.0 由 31.2 提高到 42.3、DeepSWE v1.1 由 74.2 提高到 77.0、ProgramBench 由 20.3 提高到 29.1。官方评测使用最高思考深度，接口不指定时默认为 high [12]。

MiniMax M3.1 Flash

MiniMax 于 2026 年 10 月 19 日上线接口、10 月 23 日开放权重；MoE 架构，总参数约 428B、每 token 激活约 23B，上下文 1M，思考不能关闭，不指定时默认最高深度 [19]。厂商称 M3.1 Flash 沿用前代 M3 的核心架构，只做了三处改动：全部层改为稀疏注意力，路由专家与注意力路径做量化感知训练，以 DSpark 投机解码代替原先的多 token 预测。这三处都面向推理速度与成本：官方称输出速度可达每秒 200 token 以上、中位数稳定在 170 以上，在线推理快近 3 倍、使用成本降低 70%。厂商把它定位于智能体任务，称其原生支持在每轮工具调用之间思考（交错思考），自报 DeepSWE v1.1 73.7、Terminal Bench 4.0 38.1、NL2Repo-Bench 61.2；前代 M3 自报 SWE-Bench Verified 80.5 [20]。

三家都没有报告与本评测题源重合的成绩（USACO、EGOI 或 FrontierCS）：DeepSeek 的技术报告只在思考深度的曲线图中给出 LiveCodeBench（未注明版本、没有数值表），Kimi 与 MiniMax 没有报告竞赛编程成绩。

归因规则

厂商声称的改进大多相对其上一代模型而言，而本评测没有评测它们的前代，因此不检验“是否比前代更好”，而检验较弱的命题：厂商声称擅长或改进的方向，在本评测对应的测量上是否表现为显著的相对优势。一条声称同时满足以下两点时，记为一致，可归因：

  • 厂商指明了它针对的能力，且能对应到某个档位或某项测量（正确率、运行效率、生成速度、输出长度等）；
  • 在这项测量上，该模型相对另一个模型的差值显著（区间不含 0），方向与声称一致；对于可直接测量的绝对数值（如生成速度），测量值与声称相符。

方向相反或测量值与声称不符时记为不一致；对应不到本评测测量的声称（如多轮的智能体编程）记为超出测量范围；只是相对前代的数量声称，记为无法检验；观测到显著差异但没有对应声称的，记为无对应声称，不作归因。三个模型在数据、规模与训练方法上同时不同，本评测没有消融实验，这种归因说明观测与声称是否相符，不说明因果。对照结果见 结果 › 厂商声称。

智能体（agent）评测

本评测是单次生成：模型读题后一次写出程序。智能体评测让模型在可执行的环境里多步行动，按最终结果判定。

评测智能体的要点

  • 环境可复现：每个任务固定代码版本、依赖和镜像，智能体与判题在同一份环境中运行。SWE-bench 取自 12 个流行 Python 仓库的 2,294 个真实 issue 与对应的修复 [21]；Terminal-Bench 2.0 的 89 个终端任务各带独立环境、人工参考解和自动测试 [25]。
  • 按结果判定，测试要充分：提交后由环境之外的隐藏测试判定。测试不足会把错误补丁判为通过：SWE-bench Verified 中 26/500 题测试不足 [26]；被判为通过的补丁有 7.8% 跑不过开发者的完整测试 [27]。SWE-bench Verified 本身是 93 名开发者从原题中筛出的 500 题 [24]。
  • 测试对智能体隐藏：智能体能看到或修改测试时会走捷径。ImpossibleBench 把测试改成与题意矛盾，能“通过”即说明作弊；能力更强的模型作弊率更高，把测试对模型隐藏后作弊率接近 0 [28]。
  • 外壳与模型一起报告：同一模型换外壳，解决率和花费都会变 [22, 23]。
  • 同时报告成本：只比准确率会鼓励昂贵的智能体，应给出准确率与成本（token、美元、时间）的取舍 [29, 30]。
  • 警惕污染：只给 issue 文本、不给代码，模型在 SWE-bench 的仓库上猜中出错文件的准确率最高 76%，换成其他仓库只有 53% [31]。
