原理

用 LiveCodeBench [1] 的官方题目、提示词和测试数据评测模型，用自己的判题程序判分，再测量通过答案的运行效率和代码指标。

题库

LiveCodeBench release_v6 中发布日期最新的 100 题。

生成

官方提示词，每题调用模型 API 1 次，提取回答中的最后一个代码块。

判题

AtCoder 答案用真实标准输入输出在独立进程中运行全部官方测试，多解题用校验器；LeetCode 答案调用给定函数。

代码分析

通过的答案绑核重跑，测 CPU 时间与峰值内存；用 Pylint、Radon、SonarQube 统计静态代码质量。

费用官方单价 × token，分峰谷的平台按调用时段计

为什么用最新的题

LiveCodeBench 持续从 AtCoder、LeetCode、Codeforces 收集比赛题并标注比赛日期，可以只用模型训练截止之后发布的题，降低训练数据污染 [1]。题库中的 100 题发布于 2025-02-15 至 2025-04-06；对发布更晚的模型仍不能排除污染。

判题

测试不充分或有误会让通过率失真 [3, 4]。本评测的判题规则如下，与 cb rejudge 相同。

适用判定
AtCoder（完整程序）每份答案作为独立 Python 进程，用真实的标准输入输出运行全部官方测试，每个测试限时 6 秒，逐 token 比对输出
LeetCode（补全函数）LCB 的函数调用判题，全部官方测试通过
abc397_d校验器：输出的 x、y 须为正整数且 x³ − y³ = N；输出 -1 时须确实无解（官方第 41 个测试的标准答案“3 0”不满足题意）
arc195_c校验器：允许任意合法摆法，逐条检查；Yes/No 须与标准答案一致

LCB 的题目与测试数据为本评测固定的版本，未修改。命令见 自定义评测。

性能测量

与 EvalPerf [5]、ENAMEL [6] 一样，只在答案正确的前提下比较效率；不同的是，这里以三个模型中最快的答案为基准，而不是专家写的参考解，所以“最快”不代表最优。

项目设置
对象判为通过的答案；每次运行的输出都须正确才计入
运行每次运行都是一个全新的 Python 3.11 进程（LCB 环境），绑定到单个 CPU 核
计时AtCoder：进程 CPU 时间（rusage）扣除启动基线 25.7 ms；LeetCode：只计 Solution 方法调用的 CPU 时间
内存进程峰值常驻内存（ru_maxrss）；空程序为 12.1 MB
重复每个测试 3 次、三个模型轮流先跑，取中位数；同一测试 3 次的离散度中位数 2.0%，P90 6.4%
可比题最慢答案扣除启动后仍 ≥ 0.1 秒的题；更小的测试耗时主要是启动开销，不比较
比较每题取最慢一个测试的 CPU 时间，除以三个模型中最快者，得相对倍数；汇总用几何平均

静态代码质量

按 Huang 等 [7] 的口径（与 cb quality 相同）：每份答案原样分析，不补 import，空答案跳过；不合成总分。

  • Pylint 3.3.5，默认配置：按类型统计问题数，即规范（C）、重构（R）、警告（W）、错误（E），以及 0–10 的总评分。
  • Radon 6.0.1 命令行：圈复杂度 [8]（radon cc -j 所有条目之和，类与它的方法各计一条）、可维护性指数 [9, 10]（0–100，越高越好）、函数数、LOC、LLOC、SLOC、注释行、空行。
  • SonarQube 10.4 Community，本机部署，默认质量配置：按软件质量统计可维护性、可靠性、安全三类问题数。
  • 汇总：全部答案、仅通过答案各自的每份平均，按难度分；仅通过答案每 100 SLOC 的问题密度（问题数之和 ÷ SLOC 之和 × 100）。
  • 补充（不属于该口径）：嵌套深度，即语法树中复合语句（if、for、while、with、try、def、class、match）的最大嵌套层数；AtCoder 题的读入方式。

这些指标只描述代码形态，不评价可读性、命名等主观项。多维度评价代码质量的做法见 RACE [11]。

智能体（agent）评测

本评测是单次生成：模型读题后一次写出程序。智能体评测让模型在可执行的环境里多步行动，按最终结果判定。

单次生成（本评测）智能体评测
输入题目描述任务描述 + 可操作的环境（代码仓库、终端）
模型做什么回复一次，给出完整程序循环“思考 → 调用工具（读文件、改代码、执行命令、跑测试）→ 观察结果”，直到提交
环境无；判题在模型之外进行每个任务一个隔离容器，固定代码版本与依赖
判定隐藏测试全部通过提交后在干净环境中运行隐藏测试；SWE-bench 要求原本失败的测试变为通过（FAIL_TO_PASS），且原本通过的测试仍通过（PASS_TO_PASS）[12]
结果取决于模型模型 + 外壳（scaffold：工具集、提示词、上下文管理、步数上限）[13, 22]
代表LiveCodeBench [1]、HumanEval [2]SWE-bench [12]、SWE-bench Verified [14]、Terminal-Bench [15]

评测智能体的要点

  • 环境可复现：每个任务固定代码版本、依赖和镜像，智能体与判题在同一份环境中运行。SWE-bench 取自 12 个流行 Python 仓库的 2,294 个真实 issue 与对应的修复 [12]；Terminal-Bench 2.0 的 89 个终端任务各带独立环境、人工参考解和自动测试 [15]。
  • 按结果判定，测试要充分：提交后由环境之外的隐藏测试判定。测试不足会把错误补丁判为通过：SWE-bench Verified 中 26/500 题测试不足 [17]；被判为通过的补丁有 7.8% 跑不过开发者的完整测试 [18]。SWE-bench Verified 本身是 93 名开发者从原题中筛出的 500 题 [14]。
  • 测试对智能体隐藏：智能体能看到或修改测试时会走捷径。ImpossibleBench 把测试改成与题意矛盾，能“通过”即说明作弊；能力更强的模型作弊率更高，把测试对模型隐藏后作弊率接近 0 [16]。
  • 外壳与模型一起报告：同一模型换外壳，解决率和花费都会变 [13, 22]。
  • 同时报告成本：只比准确率会鼓励昂贵的智能体，应给出准确率与成本（token、美元、时间）的取舍 [20, 21]。
  • 警惕污染：只给 issue 文本、不给代码，模型在 SWE-bench 的仓库上猜中出错文件的准确率最高 76%，换成其他仓库只有 53% [19]。

Kimi K3.1 Pro

  • 变更：在 K3 上大幅增加后训练算力，覆盖数百个领域联合 RL；重做 RL 框架、长上下文推理、沙箱、rollout 调度。
  • 官方提升方向：编程、3D 建模（直接写 Blender / CAD 脚本）、金融研究（内部 Financial Research 比 K3 高 11.6 分）、智能体。
  • 安全：中期训练与 RL 数据剔除网络安全内容；xdev-bench-hard pass@3 81.0%（不剔除 90.5%）。
  • 高速版 kimi-k3.1-pro-highspeed：速度 2–3 倍，价格 2 倍。K2 系列 2026 年底下线。
  • 使用限制：充值 ≥ 1 美元解锁；累计充值决定并发 / TPM；temperature、top_p、n、penalty 不可传。
  • 官方文档中的编程基准分数为占位符（“[xx.x%]”），无可引用数据。

DeepSeek-V4.1-Flash

  • 2026-09-10 发布：20 层因果编码器 + 20 层解码器；MoE 1 共享 + 384 路由专家，每 token 激活 6 个；KV 缓存 890 字节/token，HBM 为上一代 1/4、SSD 为 1/8；原生视觉；降价；V4-Flash 下线。
  • 2026-10-17 更新为 1017 版（新 / 旧）：Terminal-Bench 4.0 42.3 / 31.2，DeepSWE v1.1 77.0 / 74.2，ProgramBench 29.1 / 20.3，NL2Repo 68.2 / 65.4，HLE 42.6 / 36.8；输出更短、耗时更少；价格与调用方式不变。
  • Codeforces 3471（max 档；同表 V4-Pro 3348）。输出单价为 V4-Pro 的 30%、Kimi K3.1 Pro 的 12%。

DeepSeek-V4-Pro

  • 2026-04-24 首发；2026-08-13 GA：HLE 42.7 / 60.0（无 / 有工具），Terminal-Bench 2.1 87.9，DeepSWE 62.7，NL2Repo 61.5，Toolathlon-Verified 74.1；引入 low/high/max 三档；2026-08-16 起峰谷定价。
